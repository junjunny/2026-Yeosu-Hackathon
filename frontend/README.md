# Fieldnote · 접수부터 현장 완료까지

상담사·엔지니어·팀장이 같은 접수 기록을 이어서 사용하는 빌드 없는 HTML/CSS/JavaScript 데모입니다. 사용자 담당 코드·문서·스킬은 모두 `frontend/`에서 관리합니다. `AGENTS.md`, `HANDOFF.md`를 먼저 읽으세요.

## 실행

저장소 루트에서:

```bash
python3 -m http.server 4173 --directory frontend
```

`http://localhost:4173`으로 접속합니다. 현재 데이터·사진·서명은 같은 브라우저의 `localStorage`(`yeosu-fieldnote-chat-v2`)에만 저장됩니다. 역할/담당자 선택은 시연용이며 인증이나 기기 간 동기화 기능은 아닙니다.

## 현재 흐름

1. 상담사와 담당자를 선택합니다. 고객 이름(실구매자=실사용자), 등록 주소를 입력합니다. 현재 고장 발생 위치는 별도 선택 필드입니다.
2. 통화 원문을 채팅합니다. 전체 상담 내용을 기준으로 증상별 추가 질문을 제안하며, 답을 확인할 수 있는 질문 일부는 제외합니다. 현재는 **합성 규칙 기반 질문 보조**입니다. 실제 LLM/AgentStream 분석은 연결 전입니다.
3. 기존 통화 종료 전 재확인(방문 요청·주행 불가·자가조치 희망·일반 건 출동 선택)을 유지합니다. 사고 접수에서만 보험수리 가능 여부를 확인하며, 보험수리가 가능할 때만 가입 여부를 입력합니다. 상담사가 우선순위를 정합니다.
4. 통화 종료 즉시 원문을 잠급니다. 상담사가 ERP를 조회하고 제품명·구입 시점·과거 수리 이력을 직접 입력한 뒤 전달합니다. 조회할 수 없는 값은 사유를 적고, 없는 이력은 ‘없음’으로 기록합니다.
5. 팀장 화면에서 등록 주소·고장 발생 위치·상담 내용·초기 진단·우선순위를 보고 담당 기사를 배정합니다. 출발지 주소를 저장할 수 있습니다. 지도 API가 연결되기 전에는 거리·시간·최적 동선을 만들지 않습니다.
6. 엔지니어 담당자를 선택하고 같은 접수에서 `도착`을 입력합니다. 대화·분석 기반 체크리스트와 **브레이크·타이어 상태**를 확인하고 고객과 확인한 결과를 기록합니다.
7. **견적 전에 수리 전 사진을 여러 장** 첨부합니다. 이후 부품명·수량을 채팅 형식(`정확한 부품명 × 2`, 한 줄에 한 부품)으로 입력합니다. 등록된 가격표의 소비자가+공임을 부품비로 계산하고 출장비를 더합니다.
8. 견적 설명 → 고객 수리 진행 동의 서명 → 실제 수리 내역 → 수리 후 사진 여러 장 → 개인정보 처리 내역 확인 → ‘요청하신 수리를 잘 이행하였음을 확인했습니다’ 최종 서명 순서입니다. 두 서명을 별도로 보관합니다.

사진은 단계별 1~12장, 원본 한 장 20MB 이하입니다. 긴 변 900px 이하 JPEG로 변환한 뒤 저장합니다. 브라우저 저장 한도가 있으므로 사진 수·크기에 따라 저장 실패할 수 있습니다. 사진 저장 실패 시 해당 단계를 유지합니다. 기존 단일 사진 기록도 복원하며, 이전 견적의 가격을 새 요율로 소급 변경하지 않습니다.

고객 ID는 같은 브라우저에서 이름·등록 주소가 정확히 일치하는 기존 접수가 있을 때 재사용합니다. 실제 고객/장비 ID는 팀 API 계약으로 교체해야 합니다.

## 부품 가격표

요청한 **파밍보이 부품 가격(가공데이터)** 원본은 아직 작업 환경에 제공되지 않았습니다. 실제 금액을 임의로 넣지 않았습니다.

팀장 → 담당자·부품 가격표 관리 → `.xlsx` 선택 → 시트/제목 행 선택 → 부품명·소비자가·공임 열 선택 → 미리보기 확인 → 가격표 등록 순서입니다. 파일은 서버에 업로드하지 않고 브라우저에서 읽습니다. 제목 행은 빈 행을 제외한 ‘내용 행’ 번호입니다. 부품명 중복, 빈 금액, 음수, 수식 계산 결과가 없는 셀 등은 등록을 거부합니다. 공임이 없으면 엑셀에 숫자 `0`을 넣습니다. 가격표 변경 후에도 이미 확정한 견적은 당시 단가·출처를 보관합니다.

`.xlsx` ZIP/XML 읽기는 외부 CDN 없이 `DecompressionStream('deflate-raw')`와 `DOMParser`를 사용합니다. 해당 기능을 지원하는 최신 브라우저가 필요하며 `.xls`, 암호화 파일은 지원하지 않습니다. 원본을 받으면 실제 시트 구성·부품명·금액으로 추가 검증해야 합니다.

## 출장비와 최종 견적

| 출장 구분 | 출장비 |
| --- | ---: |
| 나주 관내 | 33,000원 |
| 전남 내 나주 외, 60km 미만 | 55,000원 |
| 전남 내 나주 외, 60km 이상~100km 미만 | 77,000원 |
| 100km 이상 또는 전남 외 | 100,000원 |

최종 청구액 = 출장비 + Σ(수량 × (소비자가 + 공임)). 작업비를 별도로 다시 청구하지 않습니다. 지도 연결 전에는 출장 지역·거리를 기사님이 확인해 입력합니다.

## 팀 API 연결 지점

- `services.js`: `replyToCounselor()`, `buildAnalysis()`. 실제 상담 질문·분석 API로 교체합니다. 분석 계약은 `diagnosis`, `similar[]`(사례 ID·출처), `history[]`, `checklist[]`, `missingInfo[]`, `searchStatus`를 유지합니다. 검색 성공 0건과 검색 실패를 구분합니다. 엔지니어 점검에는 `customerChecklist()`로 필수 브레이크·타이어 항목을 포함합니다.
- `loadState()`/`saveState()`: 접수·담당자·ERP·사진·서명 저장 API로 교체합니다. 인증/권한과 파일 저장도 백엔드 연결이 필요합니다. AgentStream·지도 비밀키는 서버에만 보관합니다.
- `route-provider.js`: 지도 제공자 결정 후 `routeConfig.endpoint`에 팀 백엔드 주소를 설정합니다. 프론트엔드에서는 지도 SDK나 특정 제공자의 비밀키를 요구하지 않습니다. 아래 계약으로 연결합니다.

```json
{
  "originAddress": "출발지 등록 주소",
  "optimize": "priority-then-travel-time",
  "stops": [
    { "caseId": "DEMO-...", "address": "고객 등록 주소", "priority": "urgent", "summary": "상담 원문" }
  ]
}
```

응답 예시(실측값을 반환할 어댑터 계약):

```json
{
  "source": "선택한 지도 서비스",
  "stops": [
    { "caseId": "DEMO-...", "distanceMeters": 1200, "durationSeconds": 300 }
  ]
}
```

`stops`는 방문 순서이며 거리·시간은 출발지/이전 방문지에서 해당 방문지까지의 구간 값입니다. 백엔드는 urgent → high → normal 우선순위를 지키고 같은 우선순위 안에서 경로 시간/거리를 최적화합니다. 누락·중복 접수, 음수/비수치 거리·시간, 우선순위 역전 응답을 거부합니다. 출발지·배정·우선순위·출동 대기 상태가 바뀌면 동선을 무효화합니다. 현재 화면의 방문 기준은 요청대로 등록 주소입니다. 실제 방문 위치를 적용할 경우 주소 계약을 별도로 합의해야 합니다.

출동 규칙은 고객 방문 요청 → 주행 불가 → 정상 검색 0건 → 유사 사례가 있고 자가조치 희망 → 그 외 상담사 선택 순서입니다. 검색 실패를 0건으로 처리하지 않습니다.

## 파일과 검증

- `app.js`, `index.html`, `style.css`: 역할·담당자 선택, 대화/ERP/사진/견적/팀장 화면.
- `services.js`, `workflow.js`: 합성 분석, 출동 판단, 필수 점검, 견적 계산, 이전 기록 복원.
- `price-import.js`: xlsx 읽기와 가격 열 확인.
- `route-provider.js`: 지도 제공자와 무관한 동선 API 계약.

검증 명령(빌드 불필요):

```bash
node --check frontend/app.js
node --check frontend/services.js
node --check frontend/workflow.js
node --check frontend/price-import.js
node --check frontend/route-provider.js
node frontend/tests/workflow.test.mjs
```

DOM 흐름 검증에는 `jsdom`이 필요합니다. 의존성은 임시 경로에 설치할 수 있습니다.

```bash
npm install --prefix /tmp/fieldnote-qa --no-audit --no-fund jsdom
FIELDNOTE_QA_PACKAGE=/tmp/fieldnote-qa/package.json node frontend/tests/ui-smoke.mjs
```

단위 테스트는 출장비 경계, 가격 계산·입력 오류, 출동 우선순위, 필수 점검, 이전 데이터 복원, 지도 응답 검증을 확인합니다. DOM 검증은 상담→최종 서명→저장 복원과 합성 xlsx 읽기를 확인합니다. 사진 압축·캔버스는 DOM 테스트에서 대체하므로 실제 기기의 사진·그림 서명과 반응형 외관은 별도 브라우저 확인이 필요합니다. `tests/fixtures/synthetic-prices.xlsx`는 검증용 합성 데이터이며 실제 가격표가 아닙니다.

실제 API·기기 간 동기화·원본 가격표는 미검증입니다. 개인정보 안내는 시연용 문구입니다. 운영 시 처리 주체·보유 기간·삭제 요청 방법 등 실제 처리 정책을 확인해 문구를 확정해야 합니다. 공개 시연에는 합성 고객 정보·사진·서명만 사용하세요.

## 스킬

`frontend/`에서 요청한 `npx skills add https://github.com/vercel-labs/skills --skill find-skills --agent codex -y`를 실행했습니다. `npx skills find frontend design` 결과에서 `anthropics/skills@frontend-design`의 출처·설치 수·저장소 평판을 확인하고 기존 설치본을 읽어 적용했습니다. 화면은 기존 Fieldnote의 남색 사이드바·보라색 액션·역할별 작업 흐름을 유지했습니다. 설치 기록은 `skills-lock.json`, 스킬은 `.agents/skills/`에 있습니다.
